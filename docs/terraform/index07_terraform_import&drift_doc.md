# Import&Drift

## 既存リソースの取り込み（terraform import）

Terraformを導入する前から手動やマネジメントコンソール経由で作成されていたリソースを、後からTerraformの管理下に取り込みたい場面があります。`terraform import`は、既存のリソースをStateファイルに登録するためのコマンドです。

```bash
terraform import aws_instance.web i-0123456789abcdef0
```

|注意点|概要|
|---|---|
|コードは自動生成されない（従来のimport）|`terraform import`はStateにリソースを登録するだけで、対応する`resource`ブロックはユーザが事前にコードとして書いておく必要がある|
|属性の不一致|importしたリソースの実際の設定と、書いておいたコードの内容が一致しないと、直後の`plan`で意図しない差分（変更計画）が表示される|
|import block|近年のバージョンでは、`import`ブロックをコードで宣言し`terraform plan -generate-config-out`と組み合わせることで、対応するコードの雛形を自動生成することも可能になっている|

importは、既存インフラを段階的にコード管理へ移行する際の重要な手段ですが、「実態とコードを一致させる」作業自体は手動での確認が必要です。

## ドリフト検知（terraform plan/refresh）

「ドリフト」とは、Terraformの管理下にあるリソースが、Terraform以外の経路（マネジメントコンソールでの手動変更、他の自動化ツールなど）によって、コード上の定義と異なる状態に変化してしまうことを指します。

|コマンド|役割|
|---|---|
|terraform plan|実行時に、まず現在のインフラの実際の状態を確認し、Stateファイルの内容と比較する。この比較によって、意図しない変更（ドリフト）が検出されると、それを解消するための変更が計画に含まれる|
|terraform apply -refresh-only|コードは変更せず、Stateファイルの内容だけを実際のインフラの状態に合わせて更新する（ドリフトを検知した上で、あえてコード側ではなくStateを実態に合わせたい場合に使用）|

ドリフトを放置すると、「plan結果が想定と異なる」「applyのたびに意図しない差分が出る」といった問題につながるため、定期的に`terraform plan`を実行してドリフトの有無を監視する運用がよく行われます。

## Stateと実際のリソースの整合性維持

Terraformの信頼性は、「Stateファイルが実際のインフラの状態を正確に反映している」という前提の上に成り立っています。この整合性を維持するための基本的な運用指針は以下の通りです。

|指針|理由|
|---|---|
|インフラへの変更は必ずTerraform経由で行う|マネジメントコンソール等での直接変更はドリフトの主要な原因になる|
|CI/CDパイプラインでの一元管理|applyの実行者・実行環境を統一し、ローカル環境からの野良apply実行を避ける|
|Stateロックの徹底|同時実行による書き込み競合を防ぐ|
|定期的なplan実行によるドリフト監視|変更が積み重なる前に早期発見する|

これらを徹底することで、「コードを見れば、実際のインフラがどうなっているか正確にわかる」という、IaCの本来のメリットを維持できます。
