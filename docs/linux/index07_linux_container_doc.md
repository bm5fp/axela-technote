# Container

コンテナは、専用の仮想マシンのような新しいOSではなく、Linuxカーネルが本来持つ複数の機能（namespace、cgroups、chrootなど）を組み合わせて「隔離された実行環境に見せかける」技術です。Dockerなどのコンテナ技術は、これらの機能の応用の上に成り立っています。

## namespace（PID, Network, Mount, UTS, IPC, User）

namespace（名前空間）は、カーネルが管理するグローバルなリソースを、プロセスグループごとに独立した「view（見え方）」として分離する仕組みです。同じホスト上で動いていても、異なるnamespaceに属するプロセスからは、互いの存在やリソースが見えません。

|namespace種別|分離対象|
|---|---|
|PID|プロセスID空間。コンテナ内では自身がPID 1として見える|
|Network|ネットワークインターフェース、ルーティングテーブル、ポート空間|
|Mount|マウントポイント（ファイルシステムの見え方）|
|UTS|ホスト名、ドメイン名|
|IPC|プロセス間通信（共有メモリ、セマフォ、メッセージキュー）の名前空間|
|User|UID/GIDのマッピング（コンテナ内rootをホストの非特権ユーザに割り当てるなど）|

コンテナランタイム（containerdやCRI-O）は、コンテナ起動時にこれらのnamespaceを新規作成（`unshare()`または`clone()`にnamespace用フラグを指定）することで、「独立したマシンのように見える」実行環境を作り出します。

## cgroups（CPU/メモリ/IOのリソース制御）

cgroups（control groups）は、プロセスグループ単位でCPU・メモリ・ディスクI/O・ネットワーク帯域などのリソース使用量を制限・計測する仕組みです。namespaceが「何が見えるか」を制御するのに対し、cgroupsは「どれだけ使えるか」を制御します。

|制御対象|概要|
|---|---|
|CPU|使用できるCPU時間の割合や、利用可能なCPUコアを制限|
|メモリ|使用可能な最大メモリ量を制限。超過時はOOM Killerが対象プロセスを終了させる|
|blkio|ディスクI/Oの帯域や優先度を制御|
|pids|生成可能なプロセス/スレッド数の上限を制御（fork爆弾対策）|

現在主流のcgroups v2では、階層構造とリソース種別ごとの制御がより統一的に扱えるよう整理されています。

## chroot / pivot_root

chrootは、プロセスから見える「ルートディレクトリ（/）」を、実際のファイルシステムの特定のサブディレクトリに変更する仕組みです。これにより、そのプロセスとその子プロセスは、chroot先のディレクトリより上の階層にアクセスできなくなります。

|コマンド|概要|
|---|---|
|chroot|ルートディレクトリを変更してコマンドを実行する|
|pivot_root|マウント済みのルートファイルシステムを、別のマウントポイントに切り替える。chrootよりも安全にルート切り替えができ、コンテナ技術で標準的に使われる|

chrootは古くからある技術ですが、単体では名前空間全体（プロセスやネットワーク等）を分離するものではなく、あくまで「ファイルシステムの見え方」を限定する仕組みです。そのため、実際のコンテナ実装では、namespaceやcgroupsと組み合わせて使われます。

## OverlayFS（レイヤ構造のファイルシステム）

OverlayFSは、複数のディレクトリ（レイヤ）を重ね合わせて、あたかも1つの統合されたファイルシステムであるかのように見せる仕組みです。Dockerのイメージ管理の中核technology として利用されています。

|レイヤ|役割|
|---|---|
|lowerdir|読み取り専用の下層（例：イメージの各レイヤ）。複数指定可能|
|upperdir|読み書き可能な上層（コンテナ実行中の変更はここに書き込まれる）|
|merged|lowerdirとupperdirを統合して見せる、実際にマウントされるビュー|

コンテナ内でファイルを変更すると、実際にはlowerdir（イメージ本体）は変更されず、変更差分だけがupperdirに書き込まれます（Copy-on-Write）。これにより、同じイメージから複数のコンテナを起動しても、イメージ本体（lowerdir）を共有しつつ、各コンテナは独立した変更を保持できるため、ディスク使用量と起動速度の両面で効率的です。コンテナを削除すると、通常upperdirの内容（＝コンテナ固有の変更）も破棄されます。

## Capabilitiesによるコンテナの権限制限

Linux Capabilitiesは、コンテナのセキュリティ強化にも直接応用されています。

コンテナ内のプロセスは、デフォルトでは全権限を持つrootとして動作しますが、Dockerやcontainerdは起動時にデフォルトで一部の危険なCapability（`CAP_SYS_ADMIN`など）を落とした状態でコンテナを起動します。

|運用|概要|
|---|---|
|--cap-drop ALL|全てのCapabilityを削除|
|--cap-add NET_BIND_SERVICE|必要な権限だけを個別に追加|

これにより、「コンテナ内はroot権限に見えるが、ホストに危害を及ぼせるような強力な操作（カーネルモジュールのロード、ネットワーク設定変更など）はできない」という最小権限の実行環境を実現しています。

## seccompによるシステムコール制限

seccomp（secure computing mode）は、プロセスが呼び出せるシステムコールの種類を制限するカーネルの仕組みです。コンテナ内で万一悪意あるプロセスが動作しても、危険なシステムコール（例：カーネルモジュールのロード、`ptrace`によるプロセス改ざんなど）自体を呼び出せなくすることで、攻撃対象領域（アタックサーフェス）を大幅に縮小できます。

|プロファイル|概要|
|---|---|
|デフォルトプロファイル|コンテナランタイムが提供する、一般的なアプリケーションに必要な最小限のシステムコールのみ許可する既定のポリシー|
|カスタムプロファイル|アプリケーション固有に許可するシステムコールをJSON形式などで細かく定義|
|Unconfined|制限なし（セキュリティ上非推奨）|

namespace・cgroups・Capabilities・seccompは、いずれも単体ではなく組み合わせて使うことで、コンテナという「軽量だが十分に隔離された」実行環境を実現しています。
