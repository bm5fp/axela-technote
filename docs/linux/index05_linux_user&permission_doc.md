# User&Permission

## ユーザ/グループ（/etc/passwd, /etc/group）

Linuxはマルチユーザを前提としたOSであり、ユーザとグループの情報がシステムファイルで管理されています。

|ファイル|内容|
|---|---|
|/etc/passwd|ユーザ名、UID、GID、ホームディレクトリ、デフォルトシェルなど（パスワードハッシュ自体は含まない）|
|/etc/shadow|パスワードハッシュや有効期限などの機密情報。rootのみ読み取り可能|
|/etc/group|グループ名、GID、所属ユーザ一覧|

`/etc/passwd` の各行は `ユーザ名:x:UID:GID:コメント:ホームディレクトリ:シェル` という形式になっており、`x` は実際のパスワードが`/etc/shadow`にあることを示します。

|コマンド|役割|
|---|---|
|useradd / usermod / userdel|ユーザの作成・変更・削除|
|groupadd / groupdel|グループの作成・削除|
|id|ユーザのUID/GID、所属グループを表示|
|whoami|現在のユーザ名を表示|

UID 0は常にroot（特権ユーザ）を意味し、通常のユーザには一意のUID/GIDが割り当てられます。

## root権限とsudo

rootは、Linuxシステム上であらゆる操作を行える特権ユーザ（UID 0）です。パーミッションチェックを原則バイパスできるため、システム全体に影響する操作（カーネルパラメータの変更、他ユーザのファイル操作など）が可能です。

直接rootとしてログイン・作業することはリスクが高いため、実運用では `sudo` コマンドを用いて「一般ユーザが一時的にroot権限でコマンドを実行する」方式が推奨されます。

|項目|概要|
|---|---|
|/etc/sudoers|sudoの利用可否・対象コマンドを制御する設定ファイル（`visudo`で編集）|
|sudo <command>|指定コマンドを一時的にroot権限で実行|
|su -|rootユーザに完全に切り替える（環境変数もrootのものに変更）|

sudoを使うことで、「誰が」「いつ」「どのコマンドを」rootとして実行したかのログ（`/var/log/auth.log`など）を残せる点も、直接rootログインに対する利点です。

## Capabilities（細分化された権限）

伝統的なUnix/Linuxの権限モデルでは、「rootかそれ以外か」という二択でした。しかしこれでは、例えば「特定のポート（1024番未満）を開くためだけの権限」を与えたいだけでも、プロセス全体にroot権限を与える必要があり、過剰な権限付与になってしまいます。

Capabilitiesは、root権限を意味のある単位に分割し、必要な権限だけを個別に付与できるようにする仕組みです。

|Capability例|許可される操作|
|---|---|
|CAP_NET_BIND_SERVICE|1024番未満の特権ポートへのバインド|
|CAP_SYS_ADMIN|多数のシステム管理操作（マウント等）を含む強力な権限|
|CAP_NET_ADMIN|ネットワークインターフェースやルーティングテーブルの操作|
|CAP_CHOWN|ファイルの所有者変更|

`getcap` / `setcap` コマンドで実行ファイルに特定のCapabilityを付与できます。

## PAM（Pluggable Authentication Modules）

PAMは、ログインやsudo、SSHなど、様々なアプリケーションの認証処理を共通のモジュール構造で扱えるようにする仕組みです。アプリケーション側は認証の実装詳細（パスワード認証か、指紋認証か、LDAP連携かなど）を意識せず、PAMの提供するAPIを呼び出すだけで済みます。

|設定ファイル|対象|
|---|---|
|/etc/pam.d/sshd|SSHログイン時の認証設定|
|/etc/pam.d/sudo|sudo実行時の認証設定|
|/etc/pam.d/common-auth|共通の認証ポリシー（Debian系）|

PAMの設定ファイルには、`auth`（本人確認）、`account`（アカウントの有効性）、`password`（パスワード変更時の処理）、`session`（セッション開始/終了時の処理）という4種類のモジュールタイプがあり、それぞれ複数のモジュールをスタックして組み合わせることができます。これにより、例えば「パスワード認証に加えて多要素認証を必須にする」といった柔軟なポリシーを、アプリケーションを改変せずに実現できます。

## SELinux / AppArmor（強制アクセス制御）

通常のパーミッション（rwxやACL）は「任意アクセス制御（DAC: Discretionary Access Control）」と呼ばれ、ファイルの所有者が自分の裁量で権限を設定できます。しかし、rootや所有者の設定ミス・侵害があった場合、これだけでは防御になりません。

SELinuxとAppArmorは、DACとは独立した「強制アクセス制御（MAC: Mandatory Access Control）」を提供するセキュリティフレームワークです。管理者があらかじめ定義したポリシーに基づき、プロセスが行える操作を、たとえrootであっても厳格に制限します。

|項目|SELinux|AppArmor|
|---|---|---|
|開発元|NSA（現RedHatが主導）|Canonical（Ubuntu系）|
|主な採用ディストリビューション|RHEL, CentOS, Fedora|Ubuntu, Debian|
|ポリシー単位|ラベル（コンテキスト）ベース。ファイルやプロセスに「タイプ」を付与し、タイプ間の許可された操作のみ実行可能|パスベース。プログラムごとにアクセス可能なファイルパスや権限を直接定義|
|学習コスト|比較的高い（ラベル設計の理解が必要）|比較的低い（プロファイルが直感的）|
