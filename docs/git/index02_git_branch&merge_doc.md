# Branch&Merge

## ブランチとは

ブランチは、特定のコミットを指し示す軽量な「ポインタ」にすぎません。他のVCSではブランチの作成にファイルのコピーを伴うことがありますが、Gitのブランチは単なるポインタであるため、作成・切り替えが非常に高速です。

|項目|概要|
|---|---|
|ブランチの実体|`refs/heads/`配下にある、特定のコミットハッシュを指す40文字（またはそれ以下）のファイル|
|HEAD|現在チェックアウトしているブランチを指すポインタ。新しいコミットを作ると、HEADが指すブランチのポインタが自動的に新しいコミットへ進む|
|コミットのたびの動き|コミットするたびに、現在のブランチの指す先が新しいコミットに更新されるだけで、ブランチという「実体」自体は変わらない|

|コマンド|役割|
|---|---|
|git branch <name>|新しいブランチを作成する（切り替えは行わない）|
|git switch <name> / git checkout <name>|ブランチを切り替える|
|git switch -c <name>|ブランチを作成して、同時に切り替える|
|git branch -d <name>|マージ済みのブランチを削除する|

## マージ（merge）

マージは、あるブランチの変更を、別のブランチに統合する操作です。

|マージの種類|概要|
|---|---|
|Fast-forward マージ|マージ先のブランチが、マージ元の履歴に対して単に「遅れているだけ」の場合に発生する。新しいマージコミットを作らず、ポインタを進めるだけで完了する|
|3-way マージ|両方のブランチで独立した変更が加えられている場合に発生する。共通の祖先コミット、両ブランチの最新コミットという3点を比較し、両方の変更を取り込んだ新しい「マージコミット」を作成する|

3-wayマージの結果作られるマージコミットは、通常のコミットと異なり2つの親コミットを持つ点が特徴です。これにより、複数の作業の流れが1つの履歴に合流したことが記録として残ります。

## コンフリクト（衝突）

コンフリクトは、マージしようとする2つのブランチが、同じファイルの同じ箇所を異なる内容に変更していた場合に発生します。

|項目|概要|
|---|---|
|自動解決できない理由|Gitは「どちらの変更を優先すべきか」を判断できないため、その箇所をマーカ（`<<<<<<<`, `=======`, `>>>>>>>`）付きでファイルに残し、開発者に手動での解決を委ねる|
|解決の流れ|コンフリクトマーカを見ながら最終的な内容を編集し、`git add`で解決済みとしてマークした上で、マージコミットを作成する|
|コンフリクトの回避|こまめに最新のブランチを取り込む（マージ・リベースする）ことで、変更の乖離を小さく保ち、コンフリクトの発生頻度や規模を抑えられる|

## リベース（rebase）

リベースは、マージとは異なるアプローチで、あるブランチの変更を別のブランチに統合するための操作です。

|項目|概要|
|---|---|
|仕組み|あるブランチのコミット群を、別のブランチの最新コミットの上に「付け替える」。実質的には、各コミットの差分を再生し、新しいコミット（元とは別のハッシュ値を持つ）として作り直す|
|マージとの違い|マージがマージコミットを作って2つの履歴を「合流」させるのに対し、リベースは履歴を一直線（リニア）に保つ|
|注意点|既にリモートで共有・push済みのコミットをリベースすると、コミットハッシュが変わってしまうため、他の開発者の履歴と食い違いが生じる。「共有前のローカルの履歴整理にはリベース、共有後の履歴統合にはマージ」という使い分けが一般的|

|操作|マージ|リベース|
|---|---|---|
|履歴の見た目|分岐と合流が残る（実際の作業の流れがわかる）|一直線になる（変更内容が追いやすい）|
|コミットハッシュ|既存のコミットは変更されない|付け替えられたコミットは新しいハッシュになる|
|安全性|共有ブランチに対して常に安全|push済みの共有コミットに対して行うと危険|

## ブランチ戦略の基礎

チーム開発では、ブランチの運用ルールをあらかじめ決めておくことで、統合作業を円滑に進めます（具体的な戦略の種類は[Collaboration](index06_git_collaboration_doc.md)を参照）。

|考え方|概要|
|---|---|
|長命ブランチ|`main`のように、常に存在し続けるブランチ。安定した状態を保つことが期待される|
|短命ブランチ（フィーチャーブランチ）|1つの機能や修正のためだけに作成し、マージ後は削除する一時的なブランチ|

短命なフィーチャーブランチを積極的に使うことで、`main`ブランチの安定性を保ちながら、複数の変更を並行して進めることができます。
