# Collaboration

## Pull Request（Merge Request）

Pull Requestは、あるブランチの変更を別のブランチ（多くは`main`）に取り込みたいという「提案」を行い、マージ前にレビュー・議論・自動テストの実行を挟むための仕組みです。GitHub/GitLabなどのホスティングサービスが提供する機能で、Git自体の機能ではありません。

|項目|概要|
|---|---|
|差分の可視化|提案されている変更内容（diff）を、レビュアが確認しやすい形で表示する|
|コメント・議論|特定の行に対してコメントを付けたり、変更の意図について議論したりできる|
|CI連携|Pull Requestの作成・更新をトリガに、自動テストやLintを実行し、結果をステータスとして表示する（[CI/CD](../general/index11_general_cicd_doc.md)を参照）|
|マージ|レビューが承認され、必要なチェックが通った後、対象ブランチへの統合を実行する|

## コードレビューの基本的な流れ

|ステップ|概要|
|---|---|
|1. フィーチャーブランチの作成|1つの変更に対して、専用のブランチを切る|
|2. コミット・push|作業内容をコミットし、リモートにpushする|
|3. Pull Requestの作成|変更内容の説明とともに、マージ先ブランチへの統合を提案する|
|4. レビュー|他の開発者がコードを確認し、コメント・修正依頼・承認を行う|
|5. 修正の反映|指摘に応じてコミットを追加し、pushする（Pull Requestは自動的に更新される）|
|6. マージ|承認後、対象ブランチにマージする|

## マージの方式

Pull Requestをマージする際、履歴をどう残すかにいくつかの選択肢があります。

|方式|概要|
|---|---|
|Merge commit|通常のマージと同様、2つの親を持つマージコミットを作成し、フィーチャーブランチの個々のコミットもそのまま履歴に残す|
|Squash and merge|フィーチャーブランチの複数のコミットを1つにまとめてから、対象ブランチに追加する。履歴がシンプルになる一方、個々の作業過程の粒度は失われる|
|Rebase and merge|フィーチャーブランチのコミットを、対象ブランチの上にリベースしてから追加する。マージコミットを作らず、履歴を一直線に保つ|

チームやプロジェクトによって、「履歴の見やすさ」と「作業過程の追跡可能性」のどちらを優先するかに応じて、これらの方式を使い分けます。

## ブランチ戦略

チーム開発における、ブランチの作成・統合ルールの代表的なパターンです。

|戦略|概要|
|---|---|
|Git Flow|`main`（本番）、`develop`（開発の主流）、`feature/*`（機能開発）、`release/*`（リリース準備）、`hotfix/*`（緊急修正）といった、役割の異なる複数の長命ブランチを組み合わせる、比較的厳格な戦略|
|GitHub Flow|`main`ブランチと、そこから切られる短命なフィーチャーブランチのみで構成する、よりシンプルな戦略。`main`は常にデプロイ可能な状態を保つ|
|Trunk-based Development|開発者が頻繁に（1日に何度も）`main`（トランク）に対して小さな変更を統合していく戦略。長命なフィーチャーブランチを避け、未完成の機能はFeature Flagで隠す|

Git Flowはリリースサイクルが明確なプロダクト（パッケージソフトウェアなど）に、GitHub FlowやTrunk-based Developmentは継続的にデプロイを行うWebサービスなどに向いているとされ、デプロイ頻度や求められるリリース管理の厳密さに応じて選択されます。

## コミットメッセージの規約

チームで一貫したコミットメッセージの書き方を決めておくことで、履歴の可読性や自動化（変更履歴の自動生成など）がしやすくなります。

|規約|概要|
|---|---|
|Conventional Commits|`feat: `, `fix: `, `docs: `のように、変更の種類を示すプレフィックスをメッセージ冒頭に付ける規約。CHANGELOGの自動生成や、セマンティックバージョニングの自動判定と組み合わせやすい|
|Gitmoji|変更の種類を絵文字で表現する、より視覚的な規約|

これらの規約は必須ではありませんが、特にコミット数の多いプロジェクトにおいて、`git log`だけで変更の種類をざっと把握できるという利点があります。
