# AdvancedTools

## git stash

`git stash`は、まだコミットする段階にない変更を一時的に退避させ、ワーキングツリーをきれいな状態に戻すためのコマンドです。

|コマンド|役割|
|---|---|
|git stash|現在の変更（ワーキングツリー・ステージングエリア）を退避し、直前のコミットの状態に戻す|
|git stash list|退避中の変更（スタッシュ）の一覧を表示する|
|git stash pop|直近のスタッシュを取り出し、ワーキングツリーに復元する（スタッシュ自体は削除される）|
|git stash apply|スタッシュを取り出すが、スタッシュ自体は削除せずに残す|

作業途中で急に別のブランチに切り替える必要が生じた場合（緊急のバグ修正など）に、今の作業を失わずに一旦退避させる目的でよく使われます。

## git cherry-pick

`git cherry-pick`は、あるブランチの特定の1つ（または複数）のコミットだけを選び、現在のブランチに取り込むコマンドです。

|項目|概要|
|---|---|
|マージとの違い|マージがブランチ全体の変更を統合するのに対し、cherry-pickは指定した特定のコミットだけをピンポイントで取り込む|
|典型的な用途|あるブランチで行ったバグ修正を、まだリリースされていない別のリリースブランチにも同様に適用したい場合など|
|注意点|元のコミットとは異なる新しいコミットハッシュが作られるため、同じ変更が複数のブランチに別のコミットとして存在することになる|

## git submodule

Git submoduleは、あるGitリポジトリの中に、別のGitリポジトリを「特定のコミット」に固定した状態で組み込むための仕組みです。

|項目|概要|
|---|---|
|用途|複数のプロジェクトで共有したい共通ライブラリを、独立したリポジトリとして管理しつつ、利用側のプロジェクトに取り込みたい場合に使う|
|バージョン固定|サブモジュールは常に「特定のコミット」を指しており、親リポジトリ側で明示的に更新しない限り、自動的に最新化されることはない|
|運用の複雑さ|クローン時に`--recurse-submodules`が必要になる、更新の反映に追加のコマンドが必要になるなど、通常の依存関係管理より運用が煩雑になりやすい|

近年は、言語ごとのパッケージマネージャ（npm, pipなど）で依存関係を管理できる場合はそちらが優先され、submoduleは「パッケージマネージャで扱いにくい社内共通コードの共有」のような限定的な場面で使われることが多くなっています。

## git hooks

Git hooksは、コミットやpushなど特定の操作の前後に、任意のスクリプトを自動的に実行させる仕組みです。

|フック|実行タイミング|典型的な用途|
|---|---|---|
|pre-commit|コミット作成前|Lintやフォーマットチェック、コミット対象ファイルの静的解析|
|commit-msg|コミットメッセージ確定時|メッセージが規約（Conventional Commitsなど）に沿っているかの検証|
|pre-push|push実行前|テストの実行、特定ブランチへの直接pushの禁止|

フックは各開発者の`.git/hooks/`ディレクトリにローカルに配置されるため、リポジトリをクローンしただけでは自動的に有効になりません。チーム全体で共有・強制するには、`husky`のような専用ツールや、サーバ側（CI）でのチェックと組み合わせるのが一般的です。

## インタラクティブリベース（rebase -i）

`git rebase -i`（インタラクティブリベース）は、単にコミットを付け替えるだけでなく、コミット履歴そのものを編集するための機能です。

|操作|概要|
|---|---|
|pick|コミットをそのまま採用する|
|reword|コミットの内容は変えず、メッセージだけを編集する|
|squash|直前のコミットと統合し、1つのコミットにまとめる|
|drop|そのコミットを履歴から取り除く|
|edit|そのコミットの内容自体を修正する|

Pull Requestを作成する前に、作業中に細かく分かれた「動作確認用」「タイポ修正」といったコミットをsquashでまとめ、レビューしやすい単位に履歴を整理する、といった使い方がよく行われます。ただし[Branch\&Merge](index02_git_branch&merge_doc.md)で触れた通り、既にpush済みで他者と共有しているコミットに対して行うと、履歴の食い違いを引き起こすため注意が必要です。
