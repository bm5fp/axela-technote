# Architecture

## マスタ/ワーカプロセスモデル

Nginxは、役割の異なる2種類のプロセスで構成されています。

|プロセス|役割|
|---|---|
|マスタプロセス|設定ファイルの読み込み・検証、ワーカプロセスの起動・管理、シグナルの受信(設定リロード、停止など)を行う。自身はクライアントからのリクエストを直接処理しない|
|ワーカプロセス|実際にクライアントからの接続を受け付け、リクエスト処理を行う。マスタプロセスの子プロセスとして、通常はCPUコア数と同数起動される|

設定を変更した際は、`nginx -s reload`によりマスタプロセスへシグナルを送ることで、新しい設定を読み込んだワーカプロセスを新規起動しつつ、古いワーカプロセスは処理中のリクエストを終えてから終了する「無停止でのリロード」が行われます。

## イベント駆動アーキテクチャ

Apacheの伝統的なモデル(接続ごとにプロセス/スレッドを生成する)と異なり、Nginxは1つのワーカプロセスが多数の接続を同時に処理する、イベント駆動・非同期I/Oのモデルを採用しています。

|項目|概要|
|---|---|
|イベントループ|各ワーカプロセスは、多数のソケットの状態変化(データ受信可能、送信可能など)をOSのイベント通知の仕組み(Linuxの`epoll`など)を使って監視し、発生したイベントに応じて処理を進める|
|ノンブロッキングI/O|1つの接続の処理待ち(ディスクI/Oやレスポンス待ちなど)が、他の接続の処理をブロックしない|
|C10K問題への対応|接続ごとにプロセス/スレッドを生成する方式ではメモリ・コンテキストスイッチのコストが接続数に比例して増大するのに対し、イベント駆動モデルは少ないリソースで大量の同時接続(数万規模)を捌けることを示した設計として知られる|

このアーキテクチャにより、Nginxは静的コンテンツ配信やリバースプロキシのような、I/O待ちが多く処理自体は軽いワークロードにおいて高いスループットを発揮します。

## workerプロセスの設定（worker_processes, worker_connections）

Nginxのパフォーマンスに直結する、代表的なグローバル設定です。

|ディレクティブ|概要|
|---|---|
|worker_processes|起動するワーカプロセスの数。`auto`を指定するとCPUコア数に自動設定される|
|worker_connections|1つのワーカプロセスが同時に処理できる最大接続数（events ブロック内で指定）|
|worker_rlimit_nofile|ワーカプロセスが開けるファイルディスクリプタ数の上限（OS側の上限設定とも連動する）|

理論上の最大同時接続数は「`worker_processes` × `worker_connections`」で決まりますが、リバースプロキシとして使う場合はクライアント接続とバックエンドへの接続の両方でディスクリプタを消費するため、実質的な上限はその半分程度になる点に注意が必要です。
