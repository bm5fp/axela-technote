# ReverseProxy&LoadBalancing

## proxy_passによるリバースプロキシ

`proxy_pass`は、クライアントからのリクエストを別のサーバ（バックエンド）に転送し、その応答をクライアントに返すリバースプロキシ機能の中核となるディレクティブです。

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

|ディレクティブ|概要|
|---|---|
|proxy_pass|転送先のサーバ(URL)を指定|
|proxy_set_header|バックエンドに転送するリクエストヘッダを設定・上書きする。デフォルトではクライアントの情報がバックエンドに伝わらないため、`X-Real-IP`や`X-Forwarded-For`で明示的に引き継ぐことが多い|
|proxy_read_timeout|バックエンドからの応答を待つタイムアウト時間|

リバースプロキシとして機能させることで、Nginxを「外部からの唯一の窓口」としつつ、SSL終端やキャッシュ、複数バックエンドへの振り分けといった役割を担わせることができます。

## upstreamブロック

`upstream`ブロックは、複数のバックエンドサーバをグループ化し、1つの名前で参照できるようにする仕組みです。ロードバランシングの基盤になります。

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080 backup;
}

server {
    location / {
        proxy_pass http://backend;
    }
}
```

|パラメータ|概要|
|---|---|
|weight|サーバごとの重み付け(値が大きいほど多くのリクエストが割り当てられる)|
|max_fails / fail_timeout|指定回数連続で失敗したサーバを、指定時間だけ一時的に振り分け対象から除外する|
|backup|通常は使用せず、他の全サーバが利用不可になった場合にのみ使われる予備サーバ|

## 負荷分散アルゴリズム（round-robin, least_conn, ip_hashなど）

`upstream`ブロック内のサーバへリクエストをどう振り分けるかは、アルゴリズムによって決まります。

|アルゴリズム|概要|
|---|---|
|round-robin（デフォルト）|各サーバに順番にリクエストを割り振る。指定不要で、何も書かなければこの方式になる|
|least_conn|その時点で処理中のコネクション数が最も少ないサーバに優先的に割り振る|
|ip_hash|クライアントのIPアドレスに基づいてハッシュ値を計算し、同一クライアントは常に同じサーバに割り振られる(セッションアフィニティの実現)|
|hash（任意のキー指定）|Cookie値など任意のキーに基づいてハッシュ化し、振り分け先を決定する|

セッション情報をサーバ側でメモリ保持しているようなアプリケーションでは、`ip_hash`によって同一クライアントを毎回同じサーバに固定する(スティッキーセッション)ことで、セッション不整合を回避する運用がよく行われます。

## ヘルスチェック

ヘルスチェックは、`upstream`内のバックエンドサーバが正常に応答できる状態かどうかを確認し、異常なサーバへのリクエスト振り分けを避けるための仕組みです。

|方式|概要|
|---|---|
|パッシブヘルスチェック(OSS版標準)|実際のリクエスト処理結果を見て判定する。`max_fails`回連続で失敗すると`fail_timeout`の間そのサーバを除外する|
|アクティブヘルスチェック(Nginx Plus)|実際のクライアントリクエストとは別に、定期的に専用のチェック用リクエストをバックエンドに送信して状態を判定する。OSS版のNginxでは標準機能としては提供されない|

OSS版のNginxではアクティブヘルスチェックが標準搭載されていないため、より高度なヘルスチェックが必要な場合は、Nginx Plus(商用版)の利用や、別レイヤでのヘルスチェック機構と組み合わせることが検討されます。
