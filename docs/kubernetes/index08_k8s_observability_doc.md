# Observability

## Metrics（Metrics Server, Prometheus）

Kubernetesクラスタの稼働状況を数値として把握するための仕組みです。用途に応じて2つのレイヤのメトリクス基盤が使い分けられます。

|コンポーネント|概要|
|---|---|
|Metrics Server|各Nodeのkubeletからリソース使用量（CPU/メモリ）を収集し、`kubectl top`やHPAが参照するCore Metrics APIとして提供する軽量なコンポーネント。過去の履歴は保持しない|
|Prometheus|時系列データベースを備えた本格的な監視基盤。アプリケーションやKubernetesコンポーネントが公開する`/metrics`エンドポイントを定期的にスクレイピングし、長期間のデータを蓄積・クエリできる|

|Prometheus関連の代表的なコンポーネント|役割|
|---|---|
|kube-state-metrics|Kubernetesのリソース（Pod数、Deploymentのレプリカ状況など）の状態をメトリクスとして公開する|
|Node Exporter|各NodeのOSレベルのメトリクス（CPU、メモリ、ディスクI/O等）を公開する|
|Grafana|Prometheusなどが収集したメトリクスを可視化するダッシュボードツール（Prometheus自体ではないが、セットで使われることが多い）|

Metrics ServerがHPAなど「即時的な自動化」のためのAPIであるのに対し、Prometheusは「傾向分析やアラート」のための蓄積型の基盤という役割の違いがあります。

## Logging

コンテナのログを収集・集約する仕組みです。Kubernetesはログ収集の標準機能を持たないため、周辺のエコシステムと組み合わせて構築します。

|項目|概要|
|---|---|
|コンテナの標準出力/エラー出力|Kubernetesのベストプラクティスでは、アプリケーションはログをファイルではなく標準出力/標準エラー出力に書き出すことが推奨される|
|ログの実体|コンテナランタイムが標準出力/エラー出力をNode上のファイルとして書き出す（例：`/var/log/containers/`）|
|ログ収集エージェント|各Nodeで動作するDaemonSet（Fluentd, Fluent Bitなど）が、Node上のログファイルを収集し、Elasticsearchなどの集約先に転送する|
|サイドカーパターン|メインコンテナと同じPod内にログ転送用のコンテナを同居させ、アプリケーション固有の形式のログファイルを扱う場合に用いられる|

代表的な構成として、「Fluent Bit（収集）→ Elasticsearch（保存・検索）→ Kibana（可視化）」のようなEFK/ELKスタックがよく利用されます。

## Tracing

分散トレーシングは、複数のマイクロサービスをまたいで発生する1つのリクエストの流れを、サービス間の呼び出し関係と処理時間を含めて追跡する仕組みです。

|概念|概要|
|---|---|
|トレース（Trace）|1つのリクエストが複数サービスを経由する、全体の処理の流れ|
|スパン（Span）|トレース内の個々の処理単位（1つのサービス呼び出しなど）。開始・終了時刻を持つ|
|コンテキスト伝搬|サービス間の呼び出し時に、トレースIDなどの識別子をHTTPヘッダ等で引き継ぐことで、バラバラのログを1つのトレースとして紐付ける|
|OpenTelemetry|トレース・メトリクス・ログの計装（インスツルメンテーション）を統一的に扱うためのCNCF標準仕様/SDK|

マイクロサービス化が進んだKubernetes環境では、単一サービスのログだけでは「どこで遅延が発生しているか」を特定しづらくなるため、Jaeger やTempoといったトレーシングバックエンドと組み合わせて、サービス間の依存関係やボトルネックを可視化します。

## Liveness/Readiness/Startup Probe

Probeは、kubeletがコンテナの状態を定期的にチェックし、その結果に基づいてコンテナの再起動やトラフィックの制御を行うための仕組みです。

|Probe種別|判定内容|失敗時の挙動|
|---|---|---|
|Liveness Probe|コンテナが正常に動作し続けているか|失敗するとkubeletがコンテナを再起動する|
|Readiness Probe|コンテナがトラフィックを受け付けられる状態か|失敗するとService経由の通信先（Endpoint）からそのPodが一時的に除外される（コンテナ自体は再起動されない）|
|Startup Probe|起動に時間がかかるアプリケーションの初回起動が完了したか|成功するまではLiveness/Readiness Probeの判定を保留し、起動途中の誤った再起動を防ぐ|

|チェック方式|概要|
|---|---|
|httpGet|指定したパスにHTTPリクエストを送り、成功ステータス（2xx/3xx）かどうかで判定|
|tcpSocket|指定したポートへのTCP接続が確立できるかで判定|
|exec|コンテナ内で指定したコマンドを実行し、終了コード0を正常とみなす|

これらのProbeを適切に設定することで、「起動直後でまだ準備ができていないPodにトラフィックが送られてしまう」「デッドロックに陥ったコンテナが自動で再起動されず放置される」といった問題を防ぐことができます。

## GKEでの特徴

GKEでは、GCPのオペレーション系マネージドサービス（Cloud Monitoring / Cloud Logging）と標準で統合されており、追加のエージェント導入なしに基本的な可観測性が得られます。

|項目|概要|
|---|---|
|Cloud Logging連携|各Podの標準出力/標準エラー出力が、デフォルトで自動的にCloud Loggingへ送信される。Node上へのログ収集エージェント（Fluent Bit）の導入も、GKEがあらかじめ組み込んでいる|
|Cloud Monitoring連携|CPU/メモリなどのリソースメトリクスに加え、Kubernetesのオブジェクトの状態（Pod数、コントローラの状態等）もCloud Monitoringのダッシュボードで確認できる|
|Google Cloud Managed Service for Prometheus|Prometheus形式のメトリクスを、自前でPrometheusサーバを構築・運用することなく収集・保存できるマネージドサービス。既存のPrometheus用エクスポータやアラートルールをほぼそのまま活用できる|
|GKE Dashboard|GCPコンソール上のGKE専用画面で、クラスタ・Node・ワークロードの状態やエラーログを横断的に確認できる|

自前でELK/EFKスタックやPrometheus+Grafanaを構築する場合と比べ、これらのマネージドサービスを使うことで運用対象のコンポーネントを減らせる一方、既存のOSSベースの監視基盤をそのまま持ち込みたい場合は、Managed Service for Prometheusのようなブリッジ機能を活用して移行コストを抑えることができます。
