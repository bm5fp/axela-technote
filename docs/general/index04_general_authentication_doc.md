# 認証方式

## 認証とは

認証（Authentication）は、「相手が誰であるか」を確認するプロセスです。よく混同される「認可（Authorization）」は、認証された相手に「何を許可するか」を決めるプロセスであり、両者は明確に異なる概念です。認証が済んで初めて、認可の判断が行われます。

## Basic認証

Basic認証は、HTTPの標準仕様で定義されている、最もシンプルな認証方式です。

|項目|概要|
|---|---|
|仕組み|`ユーザ名:パスワード`の文字列をBase64エンコードし、`Authorization: Basic <エンコード値>`というヘッダでリクエストごとに送信する|
|注意点|Base64エンコードは暗号化ではなく、誰でもデコードできる。そのため、必ずHTTPS（TLS）と組み合わせて使う必要がある|
|用途|社内ツールや管理画面など、簡易的なアクセス制限が必要な場面でよく使われる|

実装が容易な反面、パスワードそのものを（形式変換だけして）毎回送信する方式であるため、大規模なサービスの認証基盤としては不向きです。

## トークンベース認証とJWT

トークンベース認証は、一度の認証（ログイン）の後、パスワードの代わりに発行された「トークン」を使って以降のリクエストを認証する方式です。

|項目|概要|
|---|---|
|セッションIDとの違い|従来のセッションIDはサーバ側で状態（誰がログイン中か）を保持する必要があるのに対し、トークンベース認証（特にJWT）は「自己完結型」で、サーバ側に状態を持たせずに検証できる|
|JWT（JSON Web Token）|ヘッダ・ペイロード（クレーム）・署名の3部構成からなるトークン形式。ペイロードにはユーザIDや有効期限などの情報を含み、署名によって改ざんを検知できる|
|署名の検証|サーバは秘密鍵（または公開鍵）を使ってJWTの署名を検証するだけでよく、DBへの問い合わせなしにトークンの正当性を確認できる|

|JWTの構成|概要|
|---|---|
|Header|署名アルゴリズムなどのメタ情報|
|Payload|ユーザID、権限、有効期限（exp）などのクレーム（平文でBase64エンコードされているだけで、暗号化はされていない点に注意）|
|Signature|Header+Payloadに対する署名。改ざん検知に使われる|

JWTは「サーバ側に状態を持たない（ステートレス）」という利点がある一方、発行済みトークンを即座に無効化する仕組みを別途用意する必要がある（有効期限を短くする、失効リストを持つなど）という制約もあります。

## OAuth 2.0とOIDC

OAuth 2.0は、本来「認可」のためのプロトコルですが、これをベースに「認証」の機能を追加したのがOIDC（OpenID Connect）です。

|プロトコル|目的|
|---|---|
|OAuth 2.0|あるサービス（例：カレンダーアプリ）が、ユーザに代わって別のサービス（例：Googleアカウント）の特定のリソースにアクセスする権限を得るための「認可」の仕組み|
|OIDC（OpenID Connect）|OAuth 2.0の仕組みの上に、「ユーザが誰であるか」を示すID Tokenという概念を追加した、認証のための拡張仕様|

|OAuth 2.0の主な登場人物|役割|
|---|---|
|Resource Owner|リソースの持ち主（通常はユーザ）|
|Client|リソースにアクセスしたいアプリケーション|
|Authorization Server|認証を行い、アクセストークンを発行するサーバ|
|Resource Server|実際に保護されたリソースを提供するサーバ|

「Googleでログイン」のような仕組みは、多くの場合OIDCによって実現されており、ユーザは各サービス個別のパスワードを覚える必要がなく、サービス提供者はパスワード管理の責任を外部のIDプロバイダに委譲できます（シングルサインオン、SSO）。

## APIキー

APIキーは、主にサービス間（人間ではなくプログラム同士）の認証に使われる、比較的シンプルな方式です。

|項目|概要|
|---|---|
|仕組み|発行された固定の文字列を、リクエストヘッダやクエリパラメータに含めて送信する|
|ユーザ認証との違い|通常、特定のユーザではなく「どのアプリケーション/契約」からのリクエストかを識別する目的で使われる|
|運用上の注意点|APIキーは長期間有効なことが多く、漏洩時の影響が大きいため、定期的なローテーションやスコープ（権限範囲）の制限が重要になる|

APIキーは実装が容易な反面、JWTのような有効期限・署名検証の仕組みを持たないことが多く、漏洩した場合のリスク管理（失効の容易さなど）を運用でカバーする必要があります。
