# 証明書・PKI

## 公開鍵暗号の基礎

証明書・PKIの仕組みは、公開鍵暗号（非対称鍵暗号）という技術の上に成り立っています。公開鍵暗号では、数学的に対になった「公開鍵」と「秘密鍵」という2つの鍵を使います。

|鍵|性質|
|---|---|
|公開鍵|誰に渡しても良い鍵。この鍵で暗号化したデータは、対になる秘密鍵でしか復号できない|
|秘密鍵|本人だけが厳重に保管する鍵。この鍵で暗号化（署名）したデータは、対になる公開鍵で検証できる|

この仕組みにより、「事前に秘密の鍵を共有していない相手」とも、安全な通信や本人確認（署名検証）が可能になります。

## 証明書とは何か

公開鍵暗号だけでは、「その公開鍵が本当に通信したい相手のものか」を保証できません（悪意ある第三者が偽の公開鍵を配布する可能性がある）。証明書は、この公開鍵の正当性を第三者が保証するための仕組みです。

|証明書に含まれる主な情報|概要|
|---|---|
|サブジェクト（Subject）|証明書の所有者（ドメイン名や組織名など）|
|公開鍵|そのサブジェクトの公開鍵|
|発行者（Issuer）|この証明書を発行し、正当性を保証した認証局|
|有効期限|証明書が有効な期間|
|デジタル署名|発行者（認証局）が、証明書の内容に対して自身の秘密鍵で行った署名|

## CA（認証局）と証明書チェーン

CA（Certificate Authority、認証局）は、証明書の発行者として、申請者の身元確認を行った上で証明書に署名を行う、信頼の起点となる組織です。

|概念|概要|
|---|---|
|ルートCA|自己署名証明書（自分自身の秘密鍵で自分自身を署名した証明書）を持つ、信頼チェーンの最上位の認証局|
|中間CA|ルートCAから署名された証明書を持ち、実際にエンドユーザ向けの証明書に署名する認証局。ルートCAの秘密鍵を直接使うリスクを減らすための階層構造|
|証明書チェーン|「サーバ証明書 → 中間CA証明書 → ルートCA証明書」のように、署名の連鎖をたどって最終的に信頼されたルートCAに到達することを検証する仕組み|
|トラストストア|OSやブラウザにあらかじめ組み込まれている、信頼済みルートCAの証明書一覧|

クライアント（ブラウザなど）は、サーバから提示された証明書チェーンをたどり、自身のトラストストアにあるルートCAまで到達できれば、その証明書を信頼します。

## TLS/SSLハンドシェイクにおける利用

証明書は、HTTPS通信におけるTLS（Transport Layer Security）ハンドシェイクの中で、サーバ（場合によってはクライアントも）の身元確認に使われます。

|ステップ|概要|
|---|---|
|1. サーバ証明書の提示|サーバが自身の証明書（公開鍵を含む）をクライアントに送信する|
|2. 証明書の検証|クライアントが証明書チェーンをたどり、有効期限・ドメイン名の一致・失効していないかなどを確認する|
|3. 鍵交換|検証が通れば、以降の通信で使う対称鍵（共通鍵）を安全に交換する（公開鍵暗号は処理コストが高いため、実際のデータ通信そのものは高速な対称鍵暗号で行われることが多い）|
|4. 暗号化通信の開始|交換した対称鍵を使って、以降の通信内容を暗号化する|

このように、証明書は「通信の暗号化」そのものよりも、「通信相手が本当に意図した相手であるか」を保証する身元確認の役割を担っている点が重要です。

## 証明書の失効

有効期限内であっても、秘密鍵の漏洩などにより証明書を無効化したい場合があります。

|仕組み|概要|
|---|---|
|CRL（Certificate Revocation List）|失効した証明書のシリアル番号一覧をCAが公開するリスト|
|OCSP（Online Certificate Status Protocol）|個々の証明書の失効状態を、CRL全体をダウンロードせずにオンラインで問い合わせできるプロトコル|

証明書の有効期限を短く設定し頻繁に更新する運用（Let's Encryptの90日証明書など）も、失効の仕組みに頼らずリスクを抑える手段として広く使われています。
