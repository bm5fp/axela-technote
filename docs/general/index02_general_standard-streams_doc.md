# 標準ストリーム

## 標準ストリームとは

標準ストリームとは、主にUnix/Linux系OSがプロセス起動時に自動的に用意する、入出力用の3つの通信路（チャネル）の総称です。プログラムはファイルやネットワークを意識せずに、この決まった経路を通じてデータのやり取りができます。

|ストリーム|略称|ファイルディスクリプタ番号|役割|
|---|---|---|---|
|標準入力|stdin|0|プログラムへの入力データを受け取る経路|
|標準出力|stdout|1|プログラムの通常の出力結果を書き出す経路|
|標準エラー出力|stderr|2|エラーメッセージや警告など、通常の出力とは区別したい情報を書き出す経路|

## なぜ出力と入力が分かれているのか

プログラムがデータを扱う際、ファイル・キーボード・ネットワークなど入力元は様々ですが、プログラム自身はその違いを意識する必要がありません。OSが起動時にこの3つのストリームをあらかじめ「開いた状態」で用意しておき、プログラムはただこの決まった番号（ディスクリプタ）に対して読み書きするだけでよい、という抽象化がなされています。

## stdoutとstderrを分ける理由

標準出力とは別に、標準エラー出力という経路が用意されている理由は、「本来の処理結果」と「エラー・診断情報」を明確に区別して扱うためです。

|状況|意図|
|---|---|
|`command > output.txt`|標準出力だけをファイルに保存し、エラーメッセージは画面に表示させたい|
|`command 2> error.log`|エラーメッセージだけをファイルに保存し、通常の出力は画面に表示させたい|
|`command | grep pattern`|標準出力だけをパイプで次のコマンドに渡し、エラーメッセージが誤って混入しないようにしたい|

このように、出力を分けておくことで、後続の処理（パイプで繋いだり、ファイルにリダイレクトしたり）で「どちらを対象にするか」を柔軟に選べるようになっています。

## リダイレクトとの関係

シェル上でのリダイレクト（`>`, `>>`, `<`, `2>`など）は、この標準ストリームの接続先を、デフォルトの端末（画面・キーボード）から別のファイルやデバイスに繋ぎ変える操作です。

|記号|操作|
|---|---|
|`>`|標準出力の接続先をファイルに変更する（上書き）|
|`2>`|標準エラー出力の接続先をファイルに変更する|
|`<`|標準入力の接続先をファイルに変更する|
|`2>&1`|標準エラー出力を、標準出力と同じ接続先に統合する|

プログラム自身は「自分の出力先が端末なのか、ファイルなのか、パイプの先の別プログラムなのか」を意識するコードを書く必要がなく、常に同じファイルディスクリプタに書き込むだけでよい、という設計が、シェルの柔軟なリダイレクト機能を支えています。

## パイプとの関係

パイプ（`|`）は、あるコマンドの標準出力を、別のコマンドの標準入力に直接接続する仕組みです。

```bash
ps aux | grep nginx | wc -l
```

このように、複数のプログラムを標準ストリーム経由で数珠つなぎにすることで、それぞれは「自分の役割（フィルタリング、カウントなど）」だけに専念しながら、全体として複雑な処理を組み立てられます。これはUnix思想における「1つのことをうまくやる小さなプログラムを組み合わせる」という設計哲学を体現する仕組みです。

## コンテナ環境における標準ストリーム

Docker/Kubernetesのようなコンテナ環境では、標準ストリームはログ管理の基盤としても利用されています。

|項目|概要|
|---|---|
|コンテナのログ|コンテナ内のメインプロセスが標準出力・標準エラー出力に書き出した内容が、そのまま「コンテナのログ」としてコンテナランタイムに記録される|
|`docker logs`/`kubectl logs`|コンテナのファイルシステム内のログファイルを探すのではなく、この標準ストリームに書き出された内容を取得して表示している|
|ベストプラクティス|コンテナ化されたアプリケーションは、ログを独自のファイルに書き出すのではなく、標準出力/標準エラー出力に書き出すことが推奨される（ログ収集の仕組みをアプリケーションから切り離せるため）|

この設計により、アプリケーション側は「ログの保存先や収集方法」を意識する必要がなく、標準ストリームに書き出すだけで、後段の基盤（ログ収集エージェントなど）がその内容を適切に処理してくれるようになっています。
