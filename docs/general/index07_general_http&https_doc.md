# HTTP/HTTPS

## HTTPの基本構造

HTTP（HyperText Transfer Protocol）は、クライアントがリクエストを送り、サーバがレスポンスを返すという、リクエスト/レスポンス型のプロトコルです。

|要素|概要|
|---|---|
|リクエストライン|メソッド、パス、HTTPバージョンで構成される（例：`GET /index.html HTTP/1.1`）|
|ヘッダ|リクエスト/レスポンスに関する付加情報（Content-Type, Authorizationなど）|
|ボディ|実際に送信するデータ（GETでは通常なし、POSTなどでよく使われる）|

|代表的なメソッド|意味|
|---|---|
|GET|リソースの取得|
|POST|リソースの作成、または処理の実行|
|PUT|リソースの置き換え（全体更新）|
|PATCH|リソースの部分更新|
|DELETE|リソースの削除|

## ステータスコード

サーバがリクエストの結果をクライアントに伝えるための3桁の数値です。先頭の数字によって大まかな分類がされています。

|範囲|分類|代表例|
|---|---|---|
|1xx|情報|100 Continue|
|2xx|成功|200 OK, 201 Created, 204 No Content|
|3xx|リダイレクト|301 Moved Permanently, 304 Not Modified|
|4xx|クライアントエラー|400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found|
|5xx|サーバエラー|500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable|

401（Unauthorized）は「認証されていない」、403（Forbidden）は「認証はされているが権限がない」という違いがあり、[認証方式](index04_general_authentication_doc.md)と[アクセス制御](index01_general_accesscontrol_doc.md)の区別に対応しています。

## HTTPS（HTTPのTLS化）

HTTPSは、HTTP通信を[証明書・PKI](index03_general_certificate&pki_doc.md)で扱うTLS（Transport Layer Security）によって暗号化したものです。

|項目|概要|
|---|---|
|暗号化|通信内容が第三者に盗聴されても、内容を読み取られない|
|改ざん検知|通信経路上でデータが書き換えられていないことを保証する|
|身元確認|接続先サーバが、証明書によって主張通りの相手であることを確認できる|

現在ではブラウザの仕様変更もあり、多くの機能（位置情報取得、Service Workerなど）がHTTPS環境でのみ利用可能になっているなど、HTTPSがWebの標準的な前提になっています。

## HTTPのバージョンによる違い

HTTPはバージョンを重ねるごとに、主にパフォーマンス面での改善が図られています。

|バージョン|主な特徴|
|---|---|
|HTTP/1.1|1つのTCPコネクション上でリクエストを直列に処理（Keep-Aliveにより接続の使い回しは可能）。ヘッダが冗長になりやすい|
|HTTP/2|1つのTCPコネクション上で複数のリクエスト/レスポンスを並行して処理できる（多重化）。ヘッダ圧縮にも対応|
|HTTP/3|トランスポート層にTCPではなくUDPベースのQUICを採用。TCPで生じる「先頭パケット喪失によるブロッキング」の問題を回避し、より低遅延な通信を実現|

バージョンが上がっても、メソッドやステータスコードといったHTTPの基本的な意味論（セマンティクス）自体は共通しており、主に「その意味論をどう効率的に伝送するか」という下位層の実装が変化している点がポイントです。

## Cookieとステートレス性

HTTPは本来「ステートレス」なプロトコルであり、1つ1つのリクエストは独立していて、サーバは過去のリクエストの状態を覚えていません。Cookieは、この制約を補い、状態を持たせるための仕組みです。

|項目|概要|
|---|---|
|Set-Cookieヘッダ|サーバがレスポンスでクライアントにCookieの保存を指示する|
|Cookieヘッダ|クライアントが以降のリクエストで自動的にCookieを付与して送信する|
|セッション管理|Cookieに含めたセッションIDを使い、サーバ側でユーザごとの状態（ログイン状態など）を管理する典型的な方法|
|属性（Secure, HttpOnly, SameSiteなど）|Cookieの送信条件やJavaScriptからのアクセス可否を制御し、セキュリティを高めるための設定|

近年はCookieの代わりに、[JWT](index04_general_authentication_doc.md)のようなトークンをAuthorizationヘッダで送る方式も広く使われており、用途やアーキテクチャ（特にAPIサーバとフロントエンドを分離した構成）に応じて使い分けられています。
